# 自动回归门禁

[Component regression](../.github/workflows/regression.yml) 保留既有 required job 名称，新增范围判断与单一公开校验。线上执行范围与耗时以真实 Actions 运行为准；跳过/轻量完成不等于执行了平台测试。

| 入口 | 验证 |
| --- | --- |
| 源码 PR / 不填版本的手动运行 | 脚本/契约、核心与适配模块 JVM/Android 定向测试与编译、实际声明的 iOS/OHOS 编译、真实宿主架构 iOS simulator 测试与 Swift typecheck |
| 纯文档 PR / main push | 轻量脚本与配置检查；未知路径保守按源码处理 |
| 手动 `archive_prebuilt=true` + 候选版本 | macOS 调用现有 `archive-prebuilt.sh`，生成完整 Maven 原字节、SHA256SUMS、production 文件 provenance；不执行公网验收 |
| Release published / 手动指定已发布版本 | verify-public 一次校验冻结归档 SHA-256、精确 tag/commit、完整 publication、公开 POM/GMM/变体；通过后独立 JitPack JVM/Android 消费和 iOS Framework/OHOS .so 最终链接；rc.19 另从精确 Git tag 下载四个 iOS Pod 独立编译及 SwiftPM Native consumer 编译 |

PR 不再反复消费旧 rc.5 基线。发布 consumer 不使用 mavenLocal、源码或 staging 替换远程依赖；consumer 是框架无关的网络/存储入口，原生宿主与 Kuikly 复用同一公开 API。当前源码字节码目标为 Java 17，旧版本限制只作为历史记录保留。

缓存、Native 下载停滞检测、有限网络重试与首失败收据遵循[共用 CI 规则](https://github.com/gycrosskit/.github/blob/main/docs/持续集成门禁.md)。不自动重跑失败的编译/行为测试，不以静默编译判断下载停滞。JUnit 必须实际执行 test case；外部 Action 固定完整 SHA，CI 不使用生产凭据，测试网络为 MockEngine 或 loopback MockWebServer。

CI 到 Eazytec 的默认与受控备用地址均可能间歇超时。本组件的 `ci-pin-fork-host.sh` 在默认地址验证成功后，也独立验证已配置的备用地址（最多三次短请求，连接 8 秒、单次总计 20 秒；只使用 curl 自带瞬态网络重试，不重试证书错误）；仅通过原域名证书、HTTP 200、公网 IPv4 和实际地址一致性校验的地址进入临时 runner 的 hosts，最多两个且去重。Gradle HTTP 客户端可在建立连接失败时尝试下一地址；未通过校验的备用地址不写入，不绕过 TLS、下载失败或编译/测试失败。此调整限本组件，不改其他组件的共用模板。

源码 R8 staging 前单独预解析 core 的公共 metadata。此下载任务使用 Gradle 8.11.1 实际读取的 `org.gradle.internal.http.connectionTimeout=10000` / `socketTimeout=60000`，该 metadata 准备任务使用 `org.gradle.internal.repository.max.tentatives=1`，将恢复交给下述有界外层，避免多个文件的内层重试先耗尽八分钟总界；其他 Gradle 调用保持原策略；`sun.net.client.*` 只约束另一路 URLConnection 下载器。[失败分类器](../scripts/ci-metadata-retry.py) 要求本次 metadata 任务的全部叶子错误均为 Eazytec TCP `Connect timed out`，最多启动三次独立预解析，逐次保留日志/回执及同 runner 精确 HTTPS URL 的有时限 HEAD 探测；TLS、HTTP、编译和混合错误不重试。探测成功不能代替 Gradle 成功，预解析耗尽仍使门禁失败，正式 publication、行为测试与三个 R8 消费者均不进入该恢复循环。此配置与恢复条件由 `verification/ci/test_cache_contract.py` 的十一组替身场景验证，线上可达性仍由实际 CI 决定。

0.1.0 / rc.1–rc.18 保留原公开消费者流程，不执行新增四 Pod 步骤，也不将该跳过计为 Pod 验证通过。rc.19 的 `verify-tagged-ios-sdk.rb` 在源码门禁只检查四个 podspec 的版本/source 合同；公开消费的 `version` 固定生产 tag，workflow ref 固定已评审的 verifier commit，两者可不同；新增 Pod/SPM 步骤独立 clone 精确生产 tag 的 metadata 并要求该 checkout 等于远程 tag SHA，逐字节核对本地元数据与 tag，两处 helper 均经现装 `pod` launcher 用 `RUBYOPT=-r...` 预加载，继承其实际 Ruby/Gem 环境，不假定 Homebrew formula 或 RubyGems 路径；helper 立即清除此预加载环境并在成功后退出，避免子进程递归或继续运行 Pod CLI。源码检查前置以尽早发现 runtime 缺失，不安装新 gem；CocoaPods `local=false`、Podfile 显式 `:git` + `:commit` 下载该 tag 解出的实际源码。每个消费者锁文件的 checkout commit、版本及安装 spec 的 source 必须一致，下载源码再与 tag 比对；每个组件自身 Swift 文件须有真实编译记录和 `BUILD SUCCEEDED`，缺 Xcode 或跳过编译会失败。`EXTERNAL SOURCES` 和 `CHECKOUT OPTIONS` 均须为固定 Git/commit，禁止 `:path` / `:podspec` 复用；proof 分开记录 verifier commit/脚本 hash 与生产 tag SHA，不能把 check-only 当公开编译。

OHOS Kotlin 编译/最终 .so 链接与 ArkTS HAR 分开验收；HAR 须由真实 Hvigor 构建并校验源码、版本、API 与依赖。系统崩溃投递、真机网络打印与上传由宿主设备另行验收。

rc.18 Maven 归档以显式 `VERSION=0.2.0-rc.18` 覆盖根 Gradle 的 rc.17 开发回退值，原生 Pods rc.17 / HAR rc.16 保持不变。[归档任务](https://github.com/gycrosskit/diagnostics/actions/runs/39590476320)固定源码 `ed5b1ce883ce598a2941096aab5ce72d92b53834`；最终 Tag 须与 provenance 的完整文件集合及逐文件摘要一致，文档与 checksum 收尾不改归档来源。现有网络 consumer 验证插件安装，新增 `recordDiagnosticsBody` 还须由宿主固定远程 rc.18 后编译实际调用，不能单凭旧 consumer 绿灯认定新 API 已验收。

以下按版本保留历史验证，不能代替当前版本或新版本的验收。

## 网络采集定向回归

源码验证覆盖请求/响应关联、环境快照、脱敏、完整正文额度、one-shot、提前关闭、流式响应及异常保真。发布前补充的解析前限深检查，用 28 KiB 的 14,000 层数组在旧候选 JAR 复现 `StackOverflowError`；新实现先检查容器深度，再调用 JSON parser，并保留根 depth=0 的原有边界及转义引号行为。

该修复的定向 JVM/Android/iOS simulator 回归执行 91 项测试（core 31/26/18，Ktor JVM 11，OkHttp JVM 5），全部通过；旧候选归档作废，重新冻结发布产物。上述是源码回归次数，不与远程消费者测试或设备验收合计。

rc.6 的 JVM JAR 为 major 61，但 Android AAR 内的 classes.jar 为 major 65；发布 Java 17 消费中两项 Android 测试在首次加载 `BoundedReportWriter` 时真实失败。rc.6 标签与附件保持不可变，修复以 rc.7 发布；归档的 `--max-jvm-major 61` 同时检查 JVM JAR 与 AAR 内 Java 字节码，不能改消费运行 JDK 掩盖这个兼容问题。

## rc.8 外部 Header 策略

`redactHeader` 完全替代默认 Header 值策略，未传入时保留既有安全规则；Body 原文和 1..32 KiB 额度复用现有回调。core commonTest 验证默认放行、外部原文/遮盖、null/异常、数量与 CR/LF 约束，以及旧九参数位置、命名、尾随 onLog 和新增回调的源码兼容。

本机 JBR 21 执行 core JVM 34、Android 29、iOS simulator 21、Ktor JVM 11、OkHttp JVM 5，共 100 项通过；core iOS arm64/OHOS API 编译通过。归档仍检查全部 JVM JAR/AAR 为 major <=61，Java 17 实际运行由 CI 单独覆盖。独立 Maven consumer 从 rc.8 起编译新增公开回调，旧版本基线不引用不存在的 API；发布后的公网文件和最终链接按现有门禁验收。

rc.11 独立消费者直接引用 `openFileChannel`，JVM/Android unit/iOS Simulator 实读临时文件并等待关闭屏障、确认批次保留；iOS Framework/OHOS .so 同时编译该入口。旧 rc.1–rc.10 回归不启用不存在的文件流 API。

可选 SDK 从 Maven rc.14 起，发布消费者对 `none` / `bugly` / `umeng` 三组执行真实 Android R8，并检查压缩 APK 中的 SPI 描述与实现类保留。只编译 AAR 或调试变体不能代替此门禁。源码 Android job 另以 `source-r8-<受测SHA>` 将 core/两个适配器的六个 root/Android publication 发布到独占 staging，再复用同一 R8 消费者；唯一版本避免跨提交读到旧产物，三组消费不重复刷新已解析的插件依赖，避免外部镜像 HEAD 超时。该项只证明源码依赖闭包，不作为公开 Maven 消费证明。

发布 Android job 的首次基础消费保留依赖刷新；后续供应商循环复用同一 job 已解析的依赖，避免对同一不可变版本反复 HEAD 导致镜像连接超时。供应商仍从独占 JitPack 仓库解析，公开文件的摘要由前置 verify-public 单独校验，不以源码 staging 或本地 Maven 替代。

rc.19 起，同一精确 tag 还复用 `verification-consumer/ios-native`：保留仓库默认 rc.1，仅在隔离副本将依赖替换为本次发布版本，先与 tag 核对输入字节并记录覆盖前后 hash。真实 `xcodebuild` 必须编译 `NativeConsumer.swift` 并成功；`Package.resolved` 的 version/revision、实际 Git checkout、下载的 Native Swift 源码须对应 tag。旧版本跳过此新增门禁；原有结果不代表 SwiftPM 已执行。

rc.19 冻结归档来自源码 `7ed971a02d643a0e842239a5cf68333d962b297d`、[run 39598458301](https://github.com/gycrosskit/diagnostics/actions/runs/39598458301)，Maven SHA-256 为 `be2ec7b80ca7756d7a949ae219fa550b1e9c2615ee251cd36f3b68e23996c01f`；完整 30 publications、86 项生产输入和 sidecar 校验通过。后续 checksum / 消费门禁提交不改变这些输入，正式 tag 与归档源 commit 通过 provenance 逐文件核对。

同源三 HAR 实际使用 DevEco 现装 Node 18.20.1、Hvigor 6.22.3、OHPM 6.0.1 和 OpenHarmony SDK 6.0.2.130/API22；源配置 target/compatible/model 对齐 API22。隔离 stage 先以本轮 Core HAR 编译两个 vendor 适配，逐字节核对两份消费中的全部 Core 13 文件，构建后 32 个输入仍等于 Git；临时 file override、HAR 摘要及工具信息随 Release 的独立 HAR provenance 留存。Hvigor 在本次私有 runtime 自引导安装 pnpm 10.27.0（npm 官方 Registry、tarball integrity 已核），没有全局工具安装或许可接受动作；不能将此写成完全没有工具下载/安装。`ohpm prepublish` 通过只证明本地预检，Registry 上架和实际安装另行验收。

源码门禁的 metadata 准备与三组 source-R8 在同一 macOS Native job 执行，复用该 job 已通过真实 Native 编译解析的同源 metadata/KLIB；保留 SHA 隔离 staging、三次/8 分钟 TCP 恢复和真实 R8 结果。先核现有 android-36 SDK，Linux 继续执行 JVM/Android 主测试及 OHOS 行为/桥接契约；没有跨 runner 搬运缓存或跳过失败。Native job 仍有 60 分钟总界，真实耗时由每轮日志记录。

OHOS 三包配套 rc.20，Maven / 四个 iOS Git Pod / Swift Package 保持 rc.19。rc.19 HAR 的 Registry 提交因缺少非空 LICENSE 被服务端拒绝，原 tag 与八项 Release 资产不覆盖；rc.20 仅复制仓库现有 Apache-2.0 LICENSE 入包并调整三 HAR/Core 依赖版本，归档检查器拒绝缺失、空、错误文本与许可元数据漂移。独立 Git tag `ohos-0.2.0-rc.20` 只固定 OHOS 源；不创建同名 GitHub Release / Maven rc.20，也不将它送入 Maven/Pod 的 version 消费入口。rc.19 Release 仅追加带 rc.20 名称的 HAR 与独立 provenance/checksums。OHOS-only PR 仍执行完整 source CI、真实 HAR 编译/预检和 Registry 下载/安装验收，不跳过任何源码门禁。
